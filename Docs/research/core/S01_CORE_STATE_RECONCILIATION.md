# S-01 Core state reconciliation

Decision: **S01_CORE_STATE_RECONCILED**. Next critical gate: **S02_BENCHMARK_REGISTRY_AND_LIFECYCLE**. This is a bounded state reconciliation, not scientific validation or a product release.

## 1. Executive state

SemantIQ Core is a heterogeneous collection of functioning contracts, deterministic computations, evidence/research services and synthetic benchmark paths. It can generate a byte-repeatable synthetic first result, transform and package evidence, calculate selected statistical contrasts, and expose local SDK/CLI/API workflows. It does not yet establish a calibrated semantic benchmark catalog, a working human-rater laboratory, human-as-subject benchmarking or valid human-AI comparison.

The current SMF/HACS/Vision producer returns hardcoded scores. Historical HACS means Human–AI Comparative Semantic Benchmark Standard; current `hacs` means an agent-resilience producer, with conflicting expansions in current documentation. Historical SMF means Semantic Maturity Framework; current docs also expand SMF differently. Name continuity is not implementation continuity.

## 3. Evidence methodology

Applied hierarchy: protected-main executable source; tests; schemas/contracts; CLI/API/SDK behavior; current documentation; governance; maintainer-supplied historical material already tracked in the repository; unimplemented research concepts. Broad package/file discovery was followed by bounded Core source inspection. Scope covers benchmark, semantiq, evidence, sandbox-contracts, generic execution providers, Python/TypeScript SDKs, Core web descriptors, storage and relevant tests. Unrelated platform domains are not counted as Core capabilities merely because they have a package directory. Cyber implementation is excluded.

Repository contains 183 workspace projects according to the locked dependency install; this is an environment observation, not a count of implemented products. Machine inventory stores capability-level paths rather than dumping all files. Source-level negative searches included HIB/HACS/SMF/CBF/WIF/QGI, human/rater/blind/randomization, judges, calibration, agreement, model/provider execution and contamination. A missing search hit is bounded negative evidence, not proof of global absence.

Historical sources inspected: [SMF handbook](../../SMF_Benchmark_Testhandbuch.pdf), 12 pages containing 84 prompt templates (12 families × 7); [SemantIQ benchmark design](../../SemantIQ-Benchmarks.pdf), 297 pages. Extracted text was searched and relevant sections read; rendered handbook page 1 and design page 205 were visually checked. Page references below use PDF page numbers, not extracted-text line numbers. The historical document contains conversational drafts, illustrative scores and ambitious claims; these are not current results, normative scientific evidence or instructions for this gate. No external literature review was performed. New scientific judgments are limited to identifying missing evidence and proposing future research, not certifying methods.

Provenance: maintainer direction plus OpenAI Codex-assisted inspection/drafting of existing project sources. No restricted inputs, external model outputs, new benchmark datasets or protected implementation were incorporated. This documentation-only inventory preserves current public/protected and licensing boundaries; it does not grant publication approval.

Specific cautions: RunsService defaults missing score to 1.0 and missing determinism to true. EvaluationsService can supply environment/seed/toolchain defaults. EvaluationLedgerEngine labels metadata reproducible on append and formats a digest as a signature; BenchmarkReportEngine likewise constructs a signature-looking string without private-key signing. BenchmarkProducerEngine derives trace/merkle/signature fields from generated identifiers rather than observed task evidence. These paths must not be conflated with the stronger bundle byte-integrity checks or an authenticated independent execution receipt.

## 12. Maturity model

Adopt the proposed M0-M6 ladder prospectively with cumulative evidence gates. Engineering component maturity remains a separate axis. A mocked producer can run and pass tests while remaining M0 as a scientific benchmark.

| Level | Meaning      | Objective promotion requirements                                                                                                                               |
| ----- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M0    | CONCEPT      | Named construct and intended use; no executable benchmark claim.                                                                                               |
| M1    | SPECIFIED    | Versioned tasks, construct, target population, rubric, metric, limitations, owner and provenance reviewed.                                                     |
| M2    | EXECUTABLE   | M1 plus input-response-evaluator pipeline and error handling; tests distinguish fixtures from measured subject outputs.                                        |
| M3    | REPRODUCIBLE | M2 plus pinned/replayable configuration, versioned inputs/evaluator, full evidence package and successful clean reproduction procedure with stated tolerances. |
| M4    | CALIBRATED   | M3 plus reference annotations, evaluator calibration, variance characterization and agreement/reliability evidence appropriate to the construct.               |
| M5    | VALIDATED    | M4 plus construct-validity dossier, robustness/held-out studies, known limitations and human/external validation where appropriate.                            |
| M6    | CORE         | M5 plus stable API/schema, longitudinal evidence, governance, release compatibility and maintenance commitment.                                                |

Each promotion must link dated, version-specific evidence, an accountable reviewer and limitations. Failed studies and counterevidence remain visible; material task/rubric/model changes trigger reevaluation. No automatic promotion from tests, integrity hashes, historical “standard” labels or current release labels. Current family levels in JSON are conservative upper bounds for the specified behavior; M2 provider TCK denotes engineering conformance, not semantic intelligence.

## 17. What SemantIQ can reliably do today

Within the tested local synthetic/supplied-data scope: produce deterministic scaffold scores and a byte-repeatable first-result artifact; serialize typed contracts; map supplied traces; store process-local run/evaluation objects; build and verify bundle integrity; compute behavioral arithmetic, matched bootstrap/sign-test contrasts and selected robustness diagnostics; expose local SDK/CLI/HTTP workflows; and track research review/claim metadata. These are engineering capabilities with stated input assumptions. They are not empirical claims about model intelligence.

## 18. What it cannot yet claim

No scientifically validated semantic/cognitive/psychometric measure, calibrated universal judge, real human-rater laboratory, administered HIB, valid human-AI comparison, robust training-contamination detection, blanket independent reproducibility, production-ready UI, real signing merely from a signature-shaped string, or external adoption merely from registry/partner seed records is established. Historical illustrative model rankings are not current results. Passing the bounded tests does not change these limits.

## 19. Immediate next gate

**S02_BENCHMARK_REGISTRY_AND_LIFECYCLE** is the single next critical gate. It must reconcile current and historical names, enumerate versioned tasks/metrics/evaluators, distinguish synthetic/partial/runtime evidence, specify promotion/retirement and ownership, and define minimum run-provenance completeness. This gate is foundational to reliable counting, honest outputs and every subsequent measurement study. It should reuse existing contracts/registries and avoid unrelated refactoring.

## 20. Open research questions

- Which narrow observable constructs deserve initial Core benchmarks, and which labels should be dropped?
- Which historical tasks admit reliable labels and valid scoring anchors rather than eloquent self-description?
- What reference sets and sampling designs establish useful evaluator calibration and acceptable error?
- When are human and model administration conditions sufficiently comparable, and when must profiles remain separate?
- What uncertainty estimators remain defensible for repeated, clustered, missing or small-sample data?
- How should contamination/anti-gaming claims be limited when provenance or training exposure is unknown?
- Which evidence fields must be captured rather than defaulted, and which artifacts can independent parties actually rerun?
